> 说明:本分析基于 `D:\DevEco_studio\ArkTavern-Reference\SillyTavern-release`(以下称 **ST**)的源码
> (`character-card-parser.js`、`validator/TavernCardValidator.js`、`endpoints/characters.js`、`public/scripts/char-data.js`)
> 与 ArkTavern 自身实现(`parser/`、`models/Character.ets`、`repositories/CharacterRepository.ets`)。

## 一、结论(TL;DR)

| 维度 | 评价 |
|------|------|
| v2/v3 **标准文本字段**覆盖 | ✅ 基本齐全 |
| **长文本是否截断丢信息** | ✅ 已修复(上限 5000 → 100000) |

## 二、SillyTavern 角色卡结构(白皮书)

### 2.1 卡片载体(两种)

- **JSON 文件**:顶层 `{ spec, spec_version, data }`。
- **PNG 文件**:把 JSON 以 **Base64** 编码写入 tEXt chunk。关键字:`chara`(V2)、`ccv3`(V3,优先读取)。见 ST `character-card-parser.js` 的 `read/write`。
  - 注:社区也有把**原始 JSON**直接塞进 tEXt `chara` 的做法(你文件夹里的卡就是这样),ST 与 ArkTavern 都能读,但**导出一律用 Base64**。

### 2.2 顶层结构

| 字段 | 类型 | 说明 |
|------|------|------|
| `spec` | `'chara_card_v1'/'v2'/'v3'` | 格式版本 |
| `spec_version` | `'2.0'` / `'3.0'`(V3 判在 `[3.0, 4.0)`) | 细版本 |
| `data.*` | object | 全部业务字段(必填容器) |
| `(V1 顶层也有扁平字段)` | — | 历史兼容 |

### 2.4 V3 独有字段

| 字段 | 类型 | App 状态(修复前 → 后) |
|------|------|----------------------|
| `nickname` | string | 缺失 → 已有 `nickname` 列 ✅ |
| `group_only_greetings` | string[] | **丢弃 → 新增列** ✅ |
| `creator_notes_multilingual` | object | **丢弃 → 新增列** ✅ |
| `source` | string[] | **丢弃 → 新增列** ✅ |
| `assets` | array | **丢弃 → 新增列** ✅(V3 资产/表情/内嵌世界书) |
| `creation_date` | int(Unix 秒) | **丢弃 → 新增列** ✅ |
| `modification_date` | int(Unix 秒) | **丢弃 → 新增列** ✅ |
| `talkativeness`(旧版放顶层/extensions) | number | 未建模,随 `extensions` 保留 ⚠️ |
| `fav`、`world`(旧版) | — | 随 `extensions` 保留 ⚠️ |

> `assets` 元素形如 `{ type, uri, name, ext }`;V3 里 **`type='tagged_lorebook'`** 时 `content` 字段可内嵌一个世界书(lorebook)。
> 这是 V3 推荐的世界书内嵌方式,与 `character_book` 并存。

### 2.5 `extensions` 与正则脚本

ST 类型 `v2CharDataExtensionInfos` 常见键:
`talkativeness`、`fav`、`world`、`depth_prompt.{depth,prompt,role}`、`regex_scripts`(数组,元素含 `findRegex/replaceString/placement/disabled/...`),
以及外部工具键:`pygmalion_id`、`github_repo`、`source_url`、`chub`、`risuai`、`sd_character_prompt`、`arktavern` 等。

- ST **原样保留**整个 `extensions` 对象。
- ArkTavern 目前**导入时丢弃**单个超过 200KB 的 extension 值(如单张《凡人修仙传》的 2.9MB `regex_scripts`)以避免 RDB 2MB 单行超限;小体积的 extension(含小 `regex_scripts`)会完整保留。
- **注意**:App 不执行 `regex_scripts`,它们只是被原样存着,不产生行为。

### 2.6 世界书 `character_book`

ST 结构(见 `char-data.js` 的 `v2WorldInfoBook` / `v2DataWorldInfoEntry`):

书级:`name`、`entries[]`、`extensions`(也含 `scan_depth`/`token_budget` 等可在生产工具中出现的字段)。

条目级标准字段:
`keys`、`secondary_keys`、`comment`、`content`、`constant`、`selective`、`insertion_order`、`enabled`、`position`、`extensions`、`id`;另有 `use_regex`。

条目 `extensions` 里 ST 还写了很多可选语义:
`position`、`exclude_recursion`、`probability`、`useProbability`、`depth`、`selectiveLogic`、`group`、`group_override`、`group_weight`、`prevent_recursion`、`delay_until_recursion`、`scan_depth`、`match_whole_words`、`use_group_scoring`、`case_sensitive`、`automation_id`、`role`、`vectorized`、`display_index`、`match_creator_notes`、`match_scenario` 等(`characters.js` 的 `convertWorldInfoToCharacterBook`)。

## 四、已实现的 v3 合规项(本轮修复)

1. **长文本不再截断**:文本类字段上限 5000 → 100000 字符
   - `parser/CharacterCardJsonParser.ets`、`models/Character.ets`、`models/Lorebook.ets`
2. **6 个 v3 独有字段落库**:`group_only_greetings` / `creator_notes_multilingual` / `source` / `assets` / `creation_date` / `modification_date`
   - 新增列,由 `V39→V40` 迁移(`database/DatabaseMigration.ets`)添加;`DATABASE_VERSION=40`
   - 模型、仓库读写(`repositories/CharacterRepository.ets`)、导入(services/CharacterService.ets)同步
3. **V3 导出补全**:`parser/CharacterCardJsonWriter.writeCharacterToV3Json` 现写出上述字段,并保留原始日期;世界书经 `exportToV3JsonWithBook` 内嵌。
4. **超大 extensions 安全清洗**:导入丢弃 >200KB 的无用 blob(防 RDB 2MB 单行超限),`V38→V39` 迁移清存量超 1MB 的 `extensions_json` 行。

## 五、仍存在的差异 / 丢信息点

按优先级排序:

### P1 世界书条目/书级的“元数据”未建模 → 导出即丢
App 的 `Lorebook` / `LorebookEntry` 模型仅保留核心字段(keys/content/constant/selective/enabled/position/priority)。
- 条目:`comment`、`insertion_order`、`case_sensitive`、`use_regex`、`id`、`extensions`(大量 ST 可选语义:probability、group、scan_depth、match_scenario 等)
- 书级:`scan_depth`、`token_budget`、`recursive_scanning`、`extensions`

后果:导入一张带复杂世界书的卡 → 编辑/再导出后这些条目细节和书参数丢失;在 SillyTavern 里写入的内部字段随之消失。
**影响面**:你文件夹里多数卡的世界书条目元数据,以及 regex 触发型世界书(`use_regex`)无法在本 App 生效。

### P2 未知 `data.*` 字段会丢(与 ST 的“保留 foreign key”哲学不同)
ST 的做法是把整张卡 `data` 尽量原样保留;App 是**白名单解析**,`data` 里不认识的新键直接丢弃。
例如某工具写入 `data.xxx` 的自定义字段,App 导入后会消失。
> 缓解:App 已把 `extensions` 作为“未知字段容器”原样保存,很多第三方数据放在 `extensions.*` 而非 `data.*` 下,这部分能保住。

### P3 `entry.position` 只保留 before/after 两种
ST 的 `position` 是自由字符串(社区常用枚举),App 用 `LorebookPosition` 枚举截断为 `before_char / after_char`,其余值丢失。

### P4 大卡导入卡顿
单张 8MB+ 的 PNG / 3MB JSON 解析在主线程执行会卡 3~5 秒(ST 没有移动端同样定位)。本轮未做 worker 化。

### P5 `extensions.regex_scripts` 数据策略
- 小值(`≤200KB`)会原样存留(数据不丢)
- 大到撑爆行的单值(如 2.9MB)会被导入时丢弃
- App 不执行它们,仅存储

## 六、建议(如需进一步对齐)

1. **世界书模型扩容**(收益最大):给 `LorebookEntry` 增加 `comment/insertion_order/case_sensitive/use_regex/originalId/extensions`,给 `Lorebook` 增加 `scan_depth/token_budget/recursive_scanning/extensions`,并同步入库与写出。这样世界书可做“无损 round-trip”。
2. **未知 `data` 兜底**:把解析时未识别的 `data.*` 键折叠进 `extensions.data.*` 或单列保留,避免 P2 丢字段。
3. **`position` 保留原字符串**:改枚举为字符串透传(或至少单独存一份原文)。
4. **导入 worker 化**:大卡解析移到 TaskPool/Worker,避免主线程卡顿。
